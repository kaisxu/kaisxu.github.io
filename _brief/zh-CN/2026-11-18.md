## [研究人员披露 Java4Shell：称 OpenJDK 的 Base64 优化路径可触发越界写入](https://calif.io/java4shell/)

Calif 团队 11 月 17 日披露 CVE-2026-114938，称 OpenJDK 在特定 x86-64 向量化 Base64 解码路径中处理异常结尾时可能越界写入堆内存；其测试据称在 Keycloak、Jenkins 等使用场景中实现远程代码执行。研究说明给出了触发机制，但**并非所有 Java 程序、CPU 或部署方式都同样可利用**；其可利用范围与官方修复状态仍需由上游通告逐项核实。运行 Java 服务者应先盘点版本与暴露的解码入口。

**推荐理由**：内存安全语言也离不开底层手写汇编；如果常见解码入口可越过运行时边界，影响面可能远超单个应用。

## [Optimizely 实验平台遭滥用，恶意脚本随客户网站的正常资源下发](https://www.theregister.com/cyber-crime/2026/11/17/optimizely-hack-turns-worlds-biggest-websites-into-malware-dispensers/5310448)

《The Register》17 日跟进披露：攻击者利用 Optimizely Web Experimentation 的注册流程漏洞，将恶意 JavaScript 注入客户项目，随后由平台自身的内容分发渠道送到访客浏览器。安全研究人员在检查的 1611 个脚本中发现 188 个含恶意代码，涉及至少 **178 家机构**，包括大型媒体与企业网站；载荷包括替换加密货币收款地址。Optimizely 称已修补漏洞、移除代码并吊销相关令牌；抽样发现数不等于所有客户均已受害。

**推荐理由**：第三方 A/B 测试脚本一旦被污染，受害者不必安装软件，只要访问看似正常的大型网站就可能暴露于攻击。

## [微软 Agent Framework 的两个 PyPI 版本被植入凭据窃取程序](https://www.aikido.dev/blog/two-malicious-agent-framework-releases-hit-pypi-in-33-minutes)

Aikido 安全团队称，PyPI 上微软 Agent Framework 的 `agent-framework` 元包 **1.26.1 和 1.26.2** 于 17 日 20:35Z 起相隔 33 分钟发布，含在 Python 启动时执行的恶意加载逻辑，试图获取 Azure、Azure DevOps 和 GitHub Actions 凭据。两个版本已被移除；受影响者不能只降级包，还要检查构建缓存、重建环境并轮换暴露的密钥。调查披露的是两个特定版本，不应推断整个框架的所有发行版都遭感染。

**推荐理由**：AI 智能体依赖包直连云权限与 CI 凭据，短暂的发布窗口也足以让自动构建把窃密代码带进生产环境。

## [《Phrack》实验：带后门的训练辅助模型可把触发行为传给下一代模型](https://phrack.org/issues/73/reflections-on-trusting-ai-a-virus-inside-an-llm_md.html)

第 73 期文章以 Qwen2.5-3B 为辅助模型，植入一组会污染训练样本的触发行为，再让后续模型分别在前一代输出上微调。作者报告：经过两次独立蒸馏跳转后，最终模型在 **31 条测试样本**中对特定攻击域名的触发率为 100%，而继续生成带传播特征训练行的比例为 27%。这是受控实验及作者提供的样本量，**不是**主流闭源模型已遭感染的证据；真正的新风险是「可信数据预处理模型」本身可成为供应链入口。

**推荐理由**：仅核查原始训练语料不足以保证安全；处理、筛选和重写语料的辅助模型，也需要来源验证与行为审计。

## [美国超大规模数据中心用电研究：403 个设施年耗电估算达 68—99 TWh](https://www.theregister.com/off-prem/2026/11/17/americas-hyperscale-bit-barns-draw-as-much-power-as-entire-states/5310471)

《The Register》17 日报道哈佛团队对美国 **403 座**超大规模数据中心的测算：按不同运行负载情景，2024 年 5 月至 2025 年 4 月合计耗电约 **68—99 TWh**，估算二氧化碳排放 **2100 万—3100 万吨**。研究结合设施容量、卫星图像与电网数据，并**未直接抄读各中心电表**；也不能从中分离出专供 AI 的耗电。这是旧时段数据在本窗口的新报道，不是 2026 年当下用电的实测值。

**推荐理由**：AI 基础设施的增长受到电网和碳排约束；关注测算口径，比把整个数据中心耗电都算作大模型训练更有用。

## [百度与高校论文：用教师模型指导小型编程智能体，减少蒸馏所需 GPU 时间](https://arxiv.org/abs/2611.21020)

百度 ERNIE 团队、香港科技大学（广州）、香港中文大学等作者 11 月 16 日提交 SWE-OPD，研究让较小的编程模型在真实代码仓库中行动，由大模型给学生已到达的状态打分并蒸馏。论文报告 Qwen3.5-9B 在 SWE-bench Pro 上从 **35.9% 提升到 39.4%**；缓存教师评分的离线方案相对在线版本减少 **59.4%—72.6%** GPU 时。它是在特定教师、数据与基准上的结果，不是任意小模型自动变强的保证。

**推荐理由**：把复杂编程能力从大模型迁往小模型，比一味扩充参数更接近可负担、可定制的本地智能体。

## [多伦多大学、Vector 与英伟达论文：尝试让 MXFP4 训练跨 GPU 逐位一致](https://arxiv.org/abs/2611.21584)

多伦多大学、Vector Institute 与 NVIDIA 的作者 11 月 16 日提交 CertiSum：先判断 MXFP4 矩阵累加在哪些位置能精确复现，再对不能认证的结果做精确重算，并保持并行布局下的求和一致。作者报告，在 Qwen3-8B-Base 的 **200 步**实验里，AMD MI350X 与 NVIDIA GB200 之间的训练状态可逐位相同；对比非确定性 MXFP4，实现增加约 **11.8%—60.5%** 的单步延迟。可复现性是收益，额外计算成本不能忽略。

**推荐理由**：低精度训练若能复现，模型调试、事故审计和跨厂商迁移才有可信的对照；这比单纯刷新吞吐数字更基础。

## [《Phrack》刊载匿名自述：回看 2003 年 Linux 内核后门投稿](https://phrack.org/issues/73/history-the-2003-linux-kernel-backdoor_md.html)

新一期《Phrack》刊出匿名作者对 **2003 年 Linux 内核后门事件**的自述，描述如何在 `wait4()` 的参数检查中把本应比较用户 ID 的 `==` 偷换成赋值 `=`，试图借一个极小的源码改动获得 root 权限；恶意修改当年没有进入正式内核。文章自称出自参与者，但身份尚未独立证实，不能把回忆细节直接当成定论。今天的编译链、依赖和代码审查仍面临同类「看上去只是一行」的信任问题。

**推荐理由**：这是计算机安全史上的经典未遂事件；对照具体代码和审核机制，比泛谈「开源更安全」更有警示性。

## [微型电子阅读器 Crosspoint Reader：ESP32-C3 上的开源固件，也遭遇 AI 投稿潮](https://www.theregister.com/software/2026/11/17/inspiring-foss-project-crosspoint-reader-has-lessons-about-tech-communities-and-llms/5310424)

Crosspoint Reader 项目负责人在 Ubuntu Summit 谈到为信用卡大小的电子阅读器开发替代固件：它支持 **11 款 ESP32-C3 设备**，报道中的安装量超过 30 万。约 400 KB RAM 的微控制器无法照搬完整 Linux，必须精打细算地实现 EPUB 阅读与设备适配。项目壮大后，大量依赖 LLM 生成的功能建议和拉取请求也给志愿维护者带来审核压力；安装量不等于活跃用户数。

**推荐理由**：一块廉价小屏幕也能变成好用的便携计算机装置；这个项目同时展示了硬件约束与 AI 降低投稿门槛的代价。

## [TotalView 开始支持 Python 并行调试，瞄准超算上的跨进程问题](https://www.theregister.com/devops/2026/11/17/python-parallel-debugging-comes-to-hpc-thanks-to-totalview-upgrade/5310564)

《The Register》17 日报道，Perforce 在 SC26 演示 TotalView 新版的 Python 支持。这款原本面向 C/C++ 与 Fortran 的 HPC 调试器，现在也能观察 Python 多线程、多进程以及 GPU 相关的并行作业，定位大型作业中某个失败进程的状态。报道提到 `mpi4py` 与 Python 新的并发能力正让 Python 更多参与超算工作流；这是一项商业调试器的功能更新，并不意味着所有 Python 程序天然获得并行加速。

**推荐理由**：大规模并行任务最难的往往不是跑起来，而是找出万千进程里出错的那个；Python 工具链正补上这块短板。
