## [美国国土安全部下令全体联邦民事机构拆除 DeepSeek，连基于它构建的第三方产品也一并清退](https://madrobot.blog/2026/10/19/us-bans-deepseek-federal-agencies-dhs-order-remove-third-party/)

美国政府已命令所有联邦民事机构从计算机中剔除 DeepSeek，并停止采购该中国实验室的 AI 及**任何基于其实现构建的第三方产品与服务**。国土安全部周一向联邦公报提交了该指令的备案，依据的是 2018 年的一部供应链法律——该法允许 DHS 将高风险技术逐出政府系统。指令编号 2026-01，由国土安全部长 Markwayne Mullin 签署，**落款日期为 2026 年 7 月 24 日，但一直对外保密到本周**，其公告定于 10 月 20 日以 DHS-2026-0628 案卷号刊出。指令要求两件事：其一，"立即生效"地把杭州深度求索人工智能及其关联公司和产品排除出采购渠道，包括机构审定产品清单、电商市场等；其二，立即从机构 IT 系统中移除 DeepSeek 及其关联方的产品，以及"使用 DeepSeek 实现开发的第三方产品和服务"。

**推荐理由**：第二条才是重点——把开源权重的下游衍生品一并视为供应链风险，等于给"谁的模型血统"设了一道联邦采购红线。

## [Linux 7.3 发布：18,765 个非合并提交、3,021 名开发者，各项指标均破纪录](https://lwn.net/Articles/1101143/)

Linus Torvalds 按期发布了 7.3 内核，并打趣说这周他总算记清了今天星期几，所以发布没有随机延期。但紧接着的 7.4 合并窗口要受点影响——他正在年度家庭度假，开窗第一天会在船上和水下度过，下午才回来合并，之后一段时间作息都会不太规律。这一版在所有维度上都是破纪录的：**18,765 个非合并提交，来自 3,021 名开发者，其中 807 人是首次向内核提交代码**。主要变更包括 binfmt_misc 的若干重要扩展、面向大型系统性能的组调度工作、新的 failfs 文件系统（所有操作一律失败）、`fchroot()` 系统调用、BPF 程序的全局 per-CPU 数据、sched_ext 子调度器特性的完成、虚拟机的工作集跟踪、ntfs3 的备用数据流支持，以及一长串 SMB 服务端改进。

**推荐理由**：首次贡献者占比超过四分之一是个异常信号，结合近期关于 LLM 辅助审查推高提交量的讨论，这个数字值得继续盯。

## [微软退出英国最大 AI 超算项目：23,040 块 GB300 建好了也没电，电网要排到 2030 年代](https://www.theregister.com/on-prem/2026/10/19/microsoft-abandons-uk-ai-supercomputer-as-grid-struggles-to-keep-up/5303824)

据《电讯报》周日首先报道，微软已终止与英国 AI 基础设施初创公司 Nscale 就埃塞克斯郡 Loughton 数据中心达成的协议，原因直白得尴尬：这个政府背书的项目没有电可用。该站点原定 2027 年投运，而此前报道显示它**可能要到 2030 年代初中期才能从电网拿到足够电力**。微软本应是这座 Nscale 宣传为"英国最大主权 AI 数据中心"的锚定客户。按 2025 年 9 月宣布的方案，设施规划在 50MW 容量内塞进 **23,040 块英伟达 GB300**，可扩展至 90MW，首批芯片原定 2027 年初到货，算力供 Azure 使用。英国电网公司 UK Power Networks 称因《公用事业法》第 105 条义务无法讨论个案，但表示"许多数据中心虽然能接入我们的配电网，却在等待我们并不拥有的国家输电网的工程"。Nscale 则坚称项目继续推进，正在为该站点寻找替代电源，并称与微软的关系"依然牢固且长期"。

**推荐理由**：主权 AI 的瓶颈已经从买不到 GPU 转成接不上电，而电网工期以十年计——这是任何资本开支都买不来的东西。

## [Mercury 3：扩散式 LLM 被证明能 scale，1,068 tokens/s、1M 上下文、每百万输出 0.7 美元](https://www.inceptionlabs.ai/blog/introducing-mercury-3)

Inception 推出 Mercury 3，称其为迄今最强的扩散式大语言模型：在一系列基准上超过 GPT-6 Luna 和 Claude Haiku 5.5，同时**快 4–8 倍，达到每秒 1,000+ token**。关键论点是扩散路线也遵循 scaling law——Mercury 3 的总参数量是 Mercury 1 的 40 倍以上，智能水平相比 Mercury 1 (mini) 提升 3 倍，但速度不变。具体数据：NVIDIA GPU 上 1,068 tokens/s；上下文 100 万 token（Mercury 2.5 为 26 万）；定价每百万输入 0.20 美元、输出 0.70 美元，上线期五折（0.10/0.35），缓存 token 再打一折。早期合作方已用于浏览器智能体、实时辅导、数据工程与网页导航。在自家生产级 web agent harness 上跑 50 个真实 Mind2Web 导航任务，Mercury 3 完成率 50%，明显高于 GPT-6.1-Sol，且消耗的 token 量和智能体步数与前沿模型相同。

**推荐理由**：自回归之外的第二条技术路线第一次拿出"同样的 scaling law 也成立"的实证，延迟敏感的智能体场景可能最先换路。

## [KVM 逃逸漏洞 PwnEscape 定级 9.3：几个畸形 IPv4 包就能从客户机打到宿主机](https://www.theregister.com/virtualization/2026/10/19/linux-kvm-guest-host-escape-rated-critical-may-represent-a-new-way-to-attack-penguin-powered-networking/5303744)

10 月初声称在 Linux KVM 中发现客户机—宿主机逃逸缺陷的研究者 Paulos Yibelo 为该漏洞命名 PwnEscape，编号 CVE-2026-99999，并警告它可能代表一种攻击 Linux 的新路径。KVM 是绝大多数超大规模云所用的虚拟化管理程序，而这个漏洞的可怕之处在于**只需发送几个畸形 IPv4 数据包即可完成逃逸**。虚拟化的全部意义就是把硬件切成互相隔离的客户机，公有云和私有云都建立在这层隔离不被突破的假设上；一旦被攻破，攻击者可能触及同一宿主机或资源池上的全部虚拟机，而且由于现在很多开发者把容器跑在 micro-VM 里做隔离，波及面还要更大。红帽的 Michael S. Tsirkin 在内核稳定分支的说明中写道："如果一个带有错误校验和元数据的包进入 IPv4 协议栈，`skb_checksum_help` 可能破坏网络头并引发一连串恶果。"安全公司 SOC Prime 的分析指出，问题根源是 Linux 允许网络包携带元数据来指示校验和操作的起止位置。

**推荐理由**：攻击面不在虚拟化层而在网络协议栈的校验和卸载路径上，这意味着同类问题可能还有一批没被翻出来。

## [CERN 与 Mistral 签署战略合作意向：用数十亿次模拟对撞训练首个对撞机物理基础模型](https://home.cern/cern-and-mistral-join-forces-to-accelerate-ai-for-science/)

欧洲核子研究中心与 Mistral 签署意向书，建立聚焦科学发现基础模型的长期战略伙伴关系。核心目标是训练一个单一的预训练"**大物理模型**"（Large Physics Model）——首个面向对撞机物理的基础模型，训练数据为大型强子对撞机上数十亿次模拟质子—质子对撞，设计上要支撑多项任务：重建粒子对撞、识别粒子、标记异常信号、评估未来探测器设计。这针对的是 LHC 数据分析的一个根本难题：今天的重建依赖一条专用算法链，逐级把探测器信号转换成物理分析所用的粒子和对象，机器学习虽早已介入各个专项环节，但基础模型有望跨整条重建链学习、用单一模型支撑多个任务。CERN 迄今已存储约**一艾字节**（百万 TB）的 LHC 实验数据，而高亮度 LHC 投运后对撞次数还将增加十倍。CERN 首席信息官 Enrica Porcari 称高能物理提供了一个能以极高严格度开发和检验 AI 的独特环境。

**推荐理由**：和"通用模型做科学"不同，这是把基础模型直接插进一条已经高度工程化的物理重建流水线去替换它——成败都会很清晰。

## [Koi：跨云异构推理集群的自校准规划器，goodput 提升 1.18 倍、每 token 成本降 20%](https://www.alphaxiv.org/abs/2610.koi-heterogeneous-llm-inference-planning)

来自 UIUC、UC Berkeley、NVIDIA、字节跳动、NYU 与 Tandemn（含 Ion Stoica、P. Brighten Godfrey）的工作，针对的是一个被低估的难题：部署一个 LLM 要在加速器、并行策略、引擎配置、副本数等**约 140 个变量**上做选择（单任务即 2^140 种配置），而且跨云、跨区、跨市场，最优方案还随负载漂移而变。Koi 用递归语言模型（RLM）层级提出假设，但把预测、打分和放置交给确定性组件；它把推理行为表示为一张**固定因果图**，连接决策（加速器、并行度）、运行时中介变量（KV cache 压力、通信开销）与结果（延迟、吞吐），每次部署都会增强或削弱带作用域的因果关系。关键设计是不跑独立试验——每次部署既服务任务也检验所涉关系。论文给出的反面数据很尖锐：用实测峰值算力和带宽标定的 roofline 模型误差可达 4.7 倍，而 Claude Opus 4.8 和 GPT-5.6 Sol 对吞吐的高估分别达 4 倍和 9 倍。真实 104 卡异构 GCP 集群上，Koi 比最强基线 goodput 高 1.18 倍、每 token 成本低 20%；消融显示纯语言模型综合分 35.3，加确定性工具 51.6，完整 Koi 为 70.8。

**推荐理由**：消融结果说明收益主要来自语言模型外围的结构而非模型本身——这对当下"套个 agent 就能调优"的思路是个有用的校正。

## [C 转 Rust 之后性能去哪了：19 个操作里 12 个慢 3% 以上，最多慢 62.2%](https://arxiv.org/abs/2610.23044)

复旦大学团队研究了一个容易被忽略的缺口：转译器能把整个 C 项目迁移成行为等价的 Rust，但**行为等价不等于性能等价**。他们在 20 个真实 C 项目及其转译结果上测量，在用于分析的八个项目中，19 个操作里有 12 个的 Rust 版本比原始 C 慢 3% 以上，最严重的慢 62.2%。通过比对执行开销画像、优化后的 LLVM IR 以及每组 C–Rust 配对的编译器优化备注，他们把这些减速归因到九类反复出现的性能问题，横跨三个方面：残留的运行时工作、错失的编译器优化、以及被照搬过来的 C 风格源码模式，并为每一类给出优化方向。随后他们把这些问题编码成可复用的优化规则，做成一个基于 LLM 的工具：先 profile 定位热点函数，再与规则模式匹配，由 LLM 检查改写前置条件后重写，且只有同时通过功能与性能验证的改写才被保留。在另外十二个留出项目的 41 个操作上，该方法在所有测试负载下保持 C 的输出一致，并让 40 个操作快于转译基线，其中 18 个反超原始 C。

**推荐理由**：自动 C→Rust 迁移正在被当作内存安全的标准答案推广，而"迁移后变慢最多六成"是推广材料里不会写的那一半。

## [Wine 被移植到 OpenBSD：几十个 64 位 Windows 程序可用，《巫师 3》重制版也跑得动](https://marc.info/?l=openbsd-ports&m=179236125692175)

Thomas Frohwein 在 openbsd-ports 邮件列表上提交了他自称"今年最出人意料的 port 提案"——Wine。突破口是 `%gs`/gsbase 问题：OpenBSD 不允许设置 gsbase，Andrii 给出的软件方案是在指令层面模拟 `%gs` 前缀，Andrii 和 Fabien 承担了主要工作。作者指出现在做这件事的条件和五到十年前不同了，因为大量 Windows 软件已经转为 64 位。目前已测试**数十个 64 位 Windows 程序，多数成功**，甚至上个月才发布的《巫师 3》重制版也能跑且表现良好（需要配合 vkd3d-proton）。最大限制是 **WoW64 不工作，32 位 Windows 软件仍然无解**——可以用 `file(1)` 判断，输出里出现 "Intel 80386 32-bit" 的就不行。内建测试暂时禁用，因为它们需要访问 X server 且多个测试会挂起。作者建议先拿 Notepad++ 这类简单的 64 位程序试水，并提醒这是自担风险的软件，在能用 `unveil(2)` 之类手段做隔离之前，最好专门建一个非特权用户来跑。

**推荐理由**：OpenBSD 以安全取向的严格内核限制闻名，绕过 gsbase 限制这件事本身比"能玩游戏了"更有技术价值。

## [Ruby gem 作者封存全部仓库：当语言本身被重新定位为"AI 时代的语言"，他退出了](https://po-ru.com/2026/10/18/why-im-no-longer-updating-this-repository)

Paul Battley 归档了自己全部 Ruby gem 的源码仓库，并写了一篇文章说明原因，供各仓库链接。他引用 Matz 2000 年的文章——"Ruby 的设计是为了让程序员快乐"——以及 2019 年访谈中的"我为人类而非机器设计 Ruby"，说自己的代码正是在那个"为人类做事"的年代写的，而那个年代已经过去。他对 Rails 生态的判断尖刻：Rails 由一个他认为观点可憎的人拥有和控制，而此人在今年 Rails World 的 keynote 上表现出对 Ruby、Rails 乃至编程本身都已失去兴趣——转而用 LLM 智能体批量产出 Rust 应用，尽管他曾把 Rust 形容为"往眼睛里倒酸"，但这不要紧，因为他根本不看生成的内容。更根本的是 Ruby 语言自身现在也大量由 LLM 智能体开发，Matz 正在把 Ruby 重新定位为"AI 时代的编程语言"，由 LLM 产出，并表示为此 LLM 需要吃进更多人类写的优质 Ruby 代码。作者写道：他不再愿意为一个正被大公司露天开采、去喂养那些产出污染它的机器的公地做贡献。

**推荐理由**：开源维护者的退出理由第一次明确指向"我的贡献会成为训练语料"，这比许可证之争更难用法律手段处理。

## [把 Arch Linux 装进 RTX Spark 笔记本：116 GiB 统一内存 CUDA 可见，只因为不想要微软账号](https://josie.lol/blog/linux-rtx-spark)

Arch 的软件包维护者 Josephine Pfeiffer 把 Arch Linux ARM 装上了华硕 ProArt P16 H7607BA——128 GB 内存、6,144 CUDA 核心、2 TB SSD 的 RTX Spark 配置。结论是：**Arch 能用，7-Zip 性能跟得上 Windows，向操作系统和 CUDA 报告的内存池同为 116.0 GiB**。动机一半是技术一半是脾气：她在 Hugging Face 上发布自己的 GGUF 量化版本（过去一个月下载超 16 万次），想在笔记本上本地跑模型、折腾 RL、量化和微调，却发现官方只支持 Windows；而她拒绝 Windows 的理由包括安装时的隐私让步、等了多年才能把任务栏放到屏幕侧边、以及系统内广告。技术路径上，她以 NVIDIA 为 Ubuntu 做的内核工作为起点，修复了点亮控制台所需的 ACPI override 分配和 framebuffer 映射，从笔记本自身的 ACPI 表推导出覆盖项，打补丁的 `hid-asus` 解决键盘，音频则需要单独的 machine driver，最后把这一切做成可引导 U 盘并扩展了上游 Archinstall 4.5。

**推荐理由**：超过 100 GiB 的 GPU 可寻址统一内存是本地跑大模型的分水岭配置，而它被锁在 Windows 上这件事现在被一个人绕开了。
