## [中国前沿模型里留下英伟达 Blackwell 的指纹：DeepSeek、月之暗面、MiniMax、蚂蚁的六个模型](https://unemploymentlabs.com/checkpoint-forensics)

Unemployment Labs（Will DePue）发布了一份纯取证报告，方法是从**已公开的模型权重本身**里恢复初始值，反推能复现这些值的硬件配置与初始种子，而不是依赖泄露或内部消息。结论：自 2026 年 4 月以来 DeepSeek、Moonshot AI、MiniMax、蚂蚁集团发布的六个模型都带有 Blackwell 硬件的数值指纹，此前同厂家的模型则匹配 Hopper 一代。逐条对应是：DeepSeek-V4-Flash 与 MiniMax-M3 匹配 Blackwell B200/B300（148 个流多处理器 SM），DeepSeek-V4-Pro、Kimi K3、Kimi K3.1-Pro、Ling-3.1-flash 匹配 GB200/GB300（152 个 SM）。对 DeepSeek-V4-Flash 和 Kimi K3 两条，他们进一步在**实体 Blackwell 芯片**上复现了匹配结果。报告也给了反向验证：24 个已公开披露硬件的模型，方法与公告全部一致；英伟达自家 Nemotron-3 Ultra 技术报告写明用 GB200 训练某阶段，读出 152 SM，与 Kimi K3 同值。边界同样写明：Hopper 指纹无法区分 H800/H100/H200（表中的 H800 是实验室自述而非本方法结论）；阿里 Qwen、智谱 GLM、腾讯、小米、StepFun 的最新模型仍读作 Hopper，美团 LongCat-2.0 自称全用 AI ASIC 算力且未见英伟达指纹。报告强调其证据只支持「获得了先进算力的访问」，**不能证明芯片所在地、获取方式或是否违反出口管制**。

**推荐理由**：这是第一次有人用可复现的数值方法、从公开权重的物理痕迹里把出口管制落地成技术证据——而方法本身可被任何人复现和反驳，其严谨程度远高于此前的「据报」。

## [Apache HTTP Server 曝关键 RCE：mod_http2 的 assign_headers() 竞态导致堆损坏，64% 云环境存在受影响资源](https://www.wiz.io/blog/cve-2026-119618-rce-apache-http-server-vulnerability)

**CVE-2026-119618**，2026-11-11 随 Apache HTTP Server 2.4.71 发布修复，属 critical 级。缺陷在 HTTP/2 模块 mod_http2 的 `assign_headers()` 函数：并发执行共享资源时同步不当，**远程未认证攻击者可触发堆内存损坏并进而实现任意代码执行**。受影响范围为 Apache HTTP Server 2.4.55 至 2.4.70，GitHub 上的独立 mod_h2 模块 2.0.8 至 2.0.42。Wiz 给出两个云上数字：**64% 的云环境存在可受此漏洞影响的资源，51% 的云环境存在公网暴露实例**（且未计入配置因素）。该漏洞由两个团队独立发现——Anthropic 的 OSS Scanner（编号 ANT-2026-MAPKT6MZ）与 Google Cloud 漏洞研究团队的 Anthony Weems、Simon Scannell，分别于 10-26 与 11-03 报告给安全团队，修复提交为 824beab。无法立即打补丁时的临时缓解措施是关闭 HTTP/2，在 httpd.conf 中把 `Protocols` 限制为 `http/1.1`、移除 h2 与 h2c 引用。同一版本的 2.4.71 还修掉了另外两个 CVE：mod_md 的空指针解引用（CVE-2026-106023，important）与一个 low 级问题。

## [Rust 1.100 稳定：never type 十年后终获稳定，Cargo 开始报告未使用的依赖](https://blog.rust-lang.org/2026/11/12/Rust-1.100.0/)

Rust 1.100.0 于 11-12 发布。头条是 **never type（`!`）在经历 10 年、5 次稳定化尝试后终于稳定**，并完成了该项目目标。它代表发散计算——后续代码不可达；`return`、`break`、`std::process::exit` 等终止控制流的表达式皆属此类型。因为不可能持有 never 类型的值，Rust 允许 never-to-any 强制转换，这让 `match option { Some(x) => x, None => return }` 这类写法成为可能；此版本起 `!` 可在任意位置命名，`Infallible` 也改为 never 类型的别名。为了能改动 `Infallible`，本次引入了一处**破坏性变更**：2024 版之前的旧版次（2015/2018/2021）也像 2024 版一样改用 never type 回落，官方称多数情况下不易察觉，但可能影响忽略返回值的泛型参数等罕见写法，也可能让编译器识别出更多不可达代码。其余稳定项包括：新增 `std::mem::conjure_zst` 作为**以 unsafe 方式创建零大小类型的专用方法**（此前只能靠 `MaybeUninit::uninit().assume_init()` transmute 之类的写法），以及新的 **DropGuard** API——持有变量与闭包，实现 `Deref`/`DerefMut`，析构时执行闭包并消费变量，另有 `dismiss` 方法可取出变量而不触发析构，适合实现全有或全无的事务式回滚（官方给出的例子是写一个失败时回滚改动的解析器）。Cargo 侧三项改进：**报告未使用的依赖**（`cargo::unused_dependencies` 默认置为 `warn`，解决 rustc `unused_crate_dependencies` lint 在 Cargo 下因依赖可能跨多个构建目标共享而产生的误报）、**减少构建缓存冲突**（build-dir 改为按构建步骤而非文件类型组织目录，并把构建配置哈希从文件名移到父目录，解决 `--features` 不同导致的重复构建与 git worktree 共享 build-dir 时的混乱）、以及 **min-publish-age 依赖冷却**——`global-min-publish-age = "3 days"` 后 Cargo 会跳过发布时间过近的版本并明确告知扣下了哪个版本（官方注明：这不是对供应链攻击的完整防御，仍需人工审阅依赖更新；crates.io 的加固项目还包括隔离支持与可疑发布自动检测）。

**推荐理由**：never type 的稳定是语言层面等了十年的事，而 Cargo 的依赖冷却则是直接回应近年 crates.io 供应链事件的机制变化——两者都不是「又一个小版本」。

## [论文：智能体服务的前缀缓存会「崩而不回」——几分钟的突发流量就让 vLLM 命中率跌到 10% 且再也回不来](https://arxiv.org/abs/2611.13412)

微软 Wen Huang 与独立研究者 Jack Liu 的工作《Bursts That Outlast Themselves: Persistent Degradation in Prefix-Cached Agent Serving》。问题是智能体把推理引擎变成了闭环：上下文每轮增长，命中率决定成本——命中只需增量 prefill 约一千 token，未命中要重算 1 万到 4 万 token。论文用**配对实验**隔离历史依赖：两条 run 共享完全相同的基线到达流，只有一条额外注入 5 分钟的突发流量。结果触目惊心——突发结束后**命中率不回升**，稳定在约 10%，吞吐掉到一半以下，积压的工作集在剩余 70 分钟里持续增长；而没被注入突发的孪生 run 全程健康（12 对中 9 对如此，反向 0 对，双侧符号检验 p = 0.00391）。机制是三重反馈闭环：按 Little 定律，响应变慢意味着并发会话数上升；会话越多，工作集越超出 KV 池；LRU 在每个会话轮到下一轮之前就把它的前缀驱逐出去，于是每一轮都变成全量重算，重算又让服务更慢。论文明确排除了「这只是过载」：关掉前缀缓存后同样的突发只产生可排空的积压；给活跃会话设上限时 0/10 次坍塌；而且 7/11 次坍塌 run 中注入的会话早已全部完成，命中率仍是 0.10–0.12（不是突发会话自己在拖后腿）。**恢复比进入更难**：限流新请求只救回 8 次里的 2 次（且需 21–23 分钟），而按 KV 池容量上限**挂起已在系统中的会话**（在轮次边界暂停）则在**每一次**坍塌 run 中于 6 分钟内把命中率恢复到 0.93–0.95。CPU offload 层能延迟但不能阻止坍塌。论文给出了一个按到达率与每轮成本拟合的**排空条件**，测得盈亏平衡点在 0.010–0.014 sessions/s。论文也坦承局限：合成 session 用随机 token，真实 trace 回放只保留长度与时序不保留内容，且只测了一种 GPU 型号。

**推荐理由**：一篇把「AI 基建为什么会在流量回落后仍然坏掉」从玄学变成可复现实验的设计论文，而且给出的运维结论反直觉——该挂起旧会话，而不是限流新流量。

## [论文：后训练策略优化的覆盖崩溃与参考重置——PPO/GRPO 为何会指数级慢](https://arxiv.org/abs/2611.14467)

哈佛 Kempner 研究所（Audrey Huang、Sham M. Kakade）、伊利诺伊大学厄巴纳-香槟分校（Nan Jiang）、加州大学圣迭戈分校（Sadhika Malladi，该文主要工作在其微软研究院任职期间完成）、微软研究院纽约（Akshay Krishnamurthy、Dylan J. Foster）的工作。核心结论有两个，都相当尖锐。**其一，覆盖崩溃（coverage collapse）**：REINFORCE（PPO 与 GRPO 的基底）可以把最优响应的概率压到接近零，而奖励仍在上升；梯度信号因此消失，收敛所需步数可能是指数级的——即便基座模型本身覆盖良好、梯度精确、且对基座做了 KL 正则化也依然如此。论文给出了一个显式构造的下界，其指数项即便在基座覆盖率为常数时仍然成立，这被认为是首个把 REINFORCE 的失败单独归因于覆盖崩溃的结果。**其二，参考重置（reference resets）**：反复把 KL 的参考策略重置为最新策略可以缓解崩溃。作者据此提出元算法 **APMD（Approximate Policy Mirror Descent）**：每轮把参考重置为当前策略，对一个正则化的 RL 子问题做近似求解，从而既能用更强的正则化（每个子问题更好解），又能通过连续重置累积出全局最优。主定理证明：只要每步的 KL 误差不超过阈值，最终策略保持镜像下降速率 `J* − J(πT) ≤ log(2C_base)/(ηT)`，且**每个中间策略都保持覆盖**——对绝大多数提示，最优响应被生成的概率不低于基座的一半。作者据此证明了带参考重置的 PPO 与 GRPO 变体是「覆盖保持」的，也证明了平方损失类算法——包括**训练 Kimi 模型的那些方法**（KimiPO、KimiPO-Norm、Rebel-OnPolicy）——是覆盖保持的。论文对实践给出的建议很具体：内循环应被视为「相对参考策略的一次局部改进」，正则化越强越稳定，因此**裁剪阈值、内循环步数、批大小这些超参应与正则化强度一起调**；而当前常见做法是内循环只走 1–4 步，并且往往完全省略正则化。作者还写明论文核心结果由人类完成，AI 模型（GPT-5.5 与 GPT-5.6）用于加速探索，Claude 与 GPT-6 用于写作辅助。

**推荐理由**：这是把「PPO/GRPO 训练不稳定」从玄学变成有下界有构造的定理的第一篇论文，而且它的结论直接指向 DeepSeek、Kimi 这些前沿团队实际在用的目标函数。

## [让大模型跑在最破的设备上：小米电视盒子 1GB 内存跑 16B MoE，2013 款 iPad Air 跑 1-bit 模型](https://github.com/hyperionaidev/smolmaxxing/)

一个开源项目的 README 全部数字都是在设备本身上实测出来的，标题很直白：「在你拥有的最小硬件上跑你能跑的最大模型」。目前支持两台设备：**小米电视盒子 S（三代）**——Amlogic S7D、4× Cortex-A55、1.9 GB 内存（约 1 GB 可用）、Android 14 无 root，日常模型 Qwen3.5-2B 在 7.7 tok/s；**2013 款 iPad Air**——Apple A7 双核、1 GB 内存（约 700 MB 可用）、iOS 12.5.7 越狱，日常模型 Bonsai-1.7B（1-bit）24–26 tok/s。两台设备都能跑 8B 与 16B 的混合专家（MoE）模型而只占约 1 GB 内存。核心手法有四：其一，**为芯片手写内核**——1-bit 查表内核、重新打包的 2-bit 与三进制格式（针对 Cortex-A55），以及针对没有点积指令的 A7 的专门版本；其二，**降低每个模型的 RAM 占用**——小模型的词表里绝大多数 token 极少被用到，于是直接丢掉那些输出行（电视盒子上还有「headless」模式，在模型运行时停掉启动器与 Google 服务）；其三，**把专家从闪存分页读入**——MoE 每个 token 只激活少数几个专家，常用的留在 RAM，其余按需从闪存读取并预取下一层，「这就是 8B 和 16B 能跑在 1 GB 上的原因」；其四，对大于 RAM 的稠密模型做**闪存流式加载**，速度就是闪存的全部带宽。所有改动都是对 llama.cpp 的补丁，需要打了补丁的 llama.cpp 才能加载那些模型文件；作者称「1-bit 内核只需要基础 NEON，闪存流式加载在任何内存大于模型的 Linux 或 Android 设备上都能用」。

**推荐理由**：这是「大模型的小型化和定制化」在硬件底层的最极端版本——不是把模型压小，而是改推理引擎去适配设备，且每个数字都可复现。

## [论文：智能体记忆蒸馏——用普通文件操作而非专用记忆工具，把成功增益放大 2.97 倍](https://arxiv.org/abs/2611.14009)

北京大学、京东、四川大学、北京理工大学、中国人民大学、香港科技大学联合的《Coding Agent Memory Post-Training II》。问题：长程任务里交互历史超出模型活跃上下文，智能体必须决定**写什么、读回什么、何时做**；而近期的做法是让智能体用专用的记忆工具或上下文压缩协议，这把在-policy 蒸馏（OPD）弱化了两端——**教师从未用过这个接口，给不出有用的指导；学生又采样不到足够有意义的记忆动作，指导落不了地**，还会引发负优势问题，把学生推离正在教的行为却不说应该换成什么。作者的解法是**用双方都已有先验的普通 Bash 与文件操作**：教师有文件操作先验，学生也有。做法是发布 **CAMG-II**——覆盖 Shop、Coding、AutoResearch、General、Visual 五个长程智能体 RL 环境的套件，每个环境除原生接口外还提供普通 Bash 访问与跨整个 episode 持久的 workspace；以及 **CAMP-II**——用完全异步的 OPD 从一个冻结教师（Qwen3.8-27B）训练单一策略跨五个环境学习这种基于文件的行为，不使用任何任务奖励。结果：**CAMG-II 上 4B 学生的平均成功率 64.6%，是前作 CAMP-I（54.2%）与全部记忆学习基线的两倍多（最强 OPD 基线的 2.97 倍增益）**，9B 版本到 66.5%。消融实验揭示了原因：换成压缩协议或专用记忆工具两者都掉到 48.2%，遮蔽记忆 token 的损失掉到 47.3%，而按同样数量随机遮蔽 token 则仍有 63.3%——说明起作用的是**记忆监督本身**而非算力预算。教师与学生对文件接口的惊讶度都最低（每 token 负对数似然 0.42，专用工具 0.91，压缩 1.40），且文件接口承载了约 21.6% 的记忆动作，是专用工具（7.8%）的三倍。迁移到外部基准：**CAMP-II-9B 在 Terminal-Bench 2.1 得分 38.0、SWE-Bench Pro V2 得分 30.1，平均 34.1，超过了参数量大得多的 Qwen3.5-35B-A3B（33.8 / 27.4，平均 30.6）**。作者也坦承局限：学生最大只到 9B，只用了一个冻结教师，更大规模或多教师场景未验证。

**推荐理由**：「用双方都熟悉的接口来蒸馏」是一个反直觉但极其省力的发现——它把 4B 学生推过了 35B 模型的平均分，且消融实验把因果关系钉得很死。

## [Pyrolog 二十周年：一个 RPython 写的 Prolog，如何反过来影响了 PyPy 的运行时](https://pypy.org/posts/2026/11/20-years-of-pyrolog.html)

PyPy 开发者 CF Bolz-Tereick 在 11-12 撰文纪念 **2006 年 11 月 12 日**——即 Pyrolog 第一个存活下来的提交进入 PyPy 仓库整整二十周年。Pyrolog 是一个用 RPython 写的 Prolog 实现，起因是欧盟研究项目承诺要在 PyPy 里做约束编程：2006 年 3 月 PyPy 的合作方 Logilab 在比利时 Louvain-la-Neuve 举办了有 Peter van Roy 与 Gecode 研究者参与的 sprint，Logilab 的人受 Van Roy/Haridi 那本书与 Van Roy 的 Prolog 实现综述启发，作者自己在杜塞尔多夫听导师 Michael Leuschel 的 Prolog 课时起了动手的念头。早期版本相当直接：合一（unification）用面向对象的 RPython 写，逻辑变量存索引、绑定存进全局数组；选择点用解释器层的异常处理器表示，回溯靠抛异常再在上层捕获；成功延续（continuation）存在堆上；为了应对 Prolog 典型的深递归，这一版依赖 RPython 的 **stackless transformation**——把宿主 C 栈的信息在接近溢出时展开到宿主堆上，展开过程中顺带做了尾调用优化。作者本人坦承 Pyrolog 从未有过真正的用户，但它牵出了若干研究，并影响了若干其他 RPython 项目，文章随后按年份追溯了从 2008 年 PyPy 侧的 JIT 进展、2009–2010 年的新 Pyrolog 架构（更多延续）、2012–2013 年的压缩项与 Unipycation、Pycket，到 2022–2024 年 RPython 实现的 Effekt，直到 2026 年的 Git 转换。

**推荐理由**：一篇二十周年的项目回顾，写的其实是 PyPy 那套「把栈搬到堆上」的运行时设计从哪里来——很多今天被当作理所当然的机制，源头是一次想把 Prolog 塞进 PyPy 的尝试。
